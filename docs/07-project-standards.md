# Project Structure Standards

SubZero enforces strict project structure standards to ensure consistency, maintainability, and scalability across all applications. These standards define where every file should be placed and how modules should organize their code.

## Strict Module Placement Rules

All modules must follow these placement standards:

### 1. Module Source Organization

Every module follows a consistent internal structure:

```
src/modules/{module-name}/
├── components/              # UI components (PascalCase names)
│   ├── ModuleComponent.tsx  # Main module component
│   ├── SubComponent.tsx     # Supporting components
│   └── index.ts             # Export all components
├── hooks/                   # React hooks (camelCase, use prefix)
│   ├── useModuleData.ts     # Data fetching hooks
│   ├── useModuleActions.ts  # Action hooks
│   └── index.ts             # Export all hooks
├── stores/                  # Zustand stores (camelCase, use prefix)
│   ├── moduleStore.ts       # Main module store
│   ├── dataStore.ts         # Data-specific store
│   └── index.ts             # Export all stores
├── utils/                   # Helper functions (camelCase)
│   ├── moduleHelpers.ts     # Module-specific utilities
│   ├── validationUtils.ts   # Validation helpers
│   └── index.ts             # Export all utilities
├── api/                     # API handlers and middleware
│   ├── handlers.ts          # API route handlers
│   ├── middleware.ts        # API middleware
│   └── index.ts             # Export all API functions
├── types/                   # TypeScript definitions (.types.ts suffix)
│   ├── module.types.ts      # Module type definitions
│   ├── api.types.ts         # API type definitions
│   └── index.ts             # Export all types
├── constants/               # Module constants (UPPER_CASE)
│   ├── MODULE_CONSTANTS.ts  # Module-specific constants
│   └── index.ts             # Export all constants
└── index.ts                 # Module entry point
```

### 2. Generated Files Placement

When modules are added to a project, files are placed according to these rules:

#### Pages Structure
```
pages/
├── api/                     # API routes generated by modules
│   ├── auth/                # Auth module endpoints
│   │   ├── login.ts         # POST /api/auth/login
│   │   ├── logout.ts        # POST /api/auth/logout
│   │   └── me.ts            # GET /api/auth/me
│   ├── {entity}/            # Entity-specific endpoints
│   │   ├── index.ts         # GET (list), POST (create)
│   │   └── [id].ts          # GET, PUT, DELETE (single entity)
│   └── _middleware.ts       # Global API middleware
├── auth/                    # Auth module pages
│   ├── login.tsx            # Login page
│   ├── signup.tsx           # Signup page
│   ├── forgot-password.tsx  # Password reset
│   └── reset-password.tsx   # Password reset confirmation
├── {entity}/                # Entity management pages
│   ├── index.tsx            # List/table view
│   ├── [id].tsx             # Detail/edit view
│   ├── create.tsx           # Create form
│   └── _layout.tsx          # Entity-specific layout
├── dashboard/               # Dashboard pages from dashboard module
│   ├── index.tsx            # Main dashboard
│   ├── analytics.tsx        # Analytics page
│   └── reports.tsx          # Reports page
├── _app.tsx                 # Next.js app component
├── _document.tsx            # Next.js document component
└── index.tsx                # Homepage
```

### 3. Configuration Standards

Configuration files follow a strict naming and organization pattern:

```
config/
├── modules/                 # Module-specific configurations
│   ├── auth.json            # Global auth configuration
│   ├── roles.json           # Role-based permissions
│   ├── tables-users.json    # Users table configuration
│   ├── tables-leads.json    # Leads table configuration
│   ├── tables-products.json # Products table configuration
│   ├── dashboard.json       # Dashboard configuration
│   └── forms-{name}.json    # Form configurations
├── database/
│   ├── schemas/             # SQL schema files
│   │   ├── auth.sql         # Auth module schema
│   │   ├── tables.sql       # Tables module schema
│   │   ├── roles.sql        # Roles module schema
│   │   └── core.sql         # Core application schema
│   ├── migrations/          # Database migration files
│   │   ├── 001_initial.sql  # Initial migration
│   │   ├── 002_add_roles.sql# Roles migration
│   │   └── 003_add_tables.sql# Tables migration
│   └── seeds/               # Seed data files
│       ├── users.sql        # Sample users
│       ├── roles.sql        # Default roles
│       └── sample_data.sql  # Sample application data
├── environments/            # Environment-specific configs
│   ├── development.json     # Development settings
│   ├── staging.json         # Staging settings
│   └── production.json      # Production settings
└── subzero.json            # Main SubZero configuration
```

#### Configuration Naming Convention

- **Module global config**: `{module}.json` (e.g., `auth.json`)
- **Entity-specific config**: `{module}-{entity}.json` (e.g., `tables-users.json`)
- **Feature-specific config**: `{module}-{feature}.json` (e.g., `forms-contact.json`)

### 4. Database Schema Standards

Every module must follow these database standards:

#### Table Naming
- Table names must be **plural** and **snake_case**
- Examples: `users`, `user_roles`, `product_categories`

#### Required Columns
All tables must include these standard columns:
```sql
CREATE TABLE example_table (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  created_by UUID REFERENCES users(id),
  updated_by UUID REFERENCES users(id),
  -- Custom columns here
);
```

#### Foreign Key Standards
- Foreign keys must follow the pattern: `{entity}_id`
- Examples: `user_id`, `product_id`, `category_id`

#### Index Standards
```sql
-- Always index foreign keys
CREATE INDEX idx_table_user_id ON table_name(user_id);

-- Index frequently searched columns
CREATE INDEX idx_table_email ON table_name(email);

-- Composite indexes for common queries
CREATE INDEX idx_table_status_date ON table_name(status, created_at);
```

### 5. Component Standards

#### File Naming
- Components: **PascalCase** (e.g., `UserTable.tsx`, `LoginForm.tsx`)
- Hooks: **camelCase** with `use` prefix (e.g., `useUserData.ts`)
- Utils: **camelCase** (e.g., `userHelpers.ts`, `validationUtils.ts`)
- Types: **camelCase** with `.types.ts` suffix (e.g., `user.types.ts`)

#### Store Standards (Zustand)
```typescript
// userStore.ts
import { create } from 'zustand';
import { persist, createJSONStorage } from 'zustand/middleware';
import { User } from '../types';

interface UserState {
  // State
  users: User[];
  isLoading: boolean;
  error: string | null;
  
  // Actions
  setUsers: (users: User[]) => void;
  addUser: (user: User) => void;
  updateUser: (id: string, updates: Partial<User>) => void;
  removeUser: (id: string) => void;
  setLoading: (loading: boolean) => void;
  setError: (error: string | null) => void;
  reset: () => void;
}

export const useUserStore = create<UserState>()(
  persist(
    (set, get) => ({
      // Initial state
      users: [],
      isLoading: false,
      error: null,
      
      // Actions
      setUsers: (users) => set({ users }),
      addUser: (user) => set((state) => ({ 
        users: [...state.users, user] 
      })),
      updateUser: (id, updates) => set((state) => ({
        users: state.users.map(user => 
          user.id === id ? { ...user, ...updates } : user
        )
      })),
      removeUser: (id) => set((state) => ({
        users: state.users.filter(user => user.id !== id)
      })),
      setLoading: (isLoading) => set({ isLoading }),
      setError: (error) => set({ error }),
      reset: () => set({ users: [], isLoading: false, error: null }),
    }),
    {
      name: 'user-store',
      storage: createJSONStorage(() => localStorage),
      partialize: (state) => ({ users: state.users }),
    }
  )
);
```

### 6. Shared Components Location

Shared components have designated locations:

```
src/
├── components/
│   ├── common/              # Shared across all modules
│   │   ├── Button.tsx       # Reusable button component
│   │   ├── Modal.tsx        # Modal component
│   │   ├── Table.tsx        # Generic table component
│   │   └── index.ts         # Export all common components
│   ├── layout/              # Layout components
│   │   ├── Header.tsx       # Application header
│   │   ├── Sidebar.tsx      # Navigation sidebar
│   │   ├── Footer.tsx       # Application footer
│   │   └── Layout.tsx       # Main layout wrapper
│   └── forms/               # Shared form components
│       ├── FormField.tsx    # Generic form field
│       ├── FormButton.tsx   # Form button component
│       └── index.ts         # Export all form components
└── modules/                 # Module-specific components
    └── {module}/
        └── components/      # Module-specific components only
```

## Enforcement and Validation

### CLI Validation
SubZero CLI validates project structure:

```bash
# Check project structure compliance
subzero-cli doctor

# Validate specific module structure
subzero-cli validate --module=tables

# Fix structure issues
subzero-cli fix --structure
```

### Pre-commit Hooks
```json
{
  "husky": {
    "hooks": {
      "pre-commit": "subzero-cli validate --strict"
    }
  }
}
```

### ESLint Rules
```javascript
// .eslintrc.js
module.exports = {
  rules: {
    'subzero/module-structure': 'error',
    'subzero/file-naming': 'error',
    'subzero/import-order': 'error'
  }
};
```

## Benefits of Strict Standards

### For Developers
- **Predictable structure**: Always know where to find files
- **Faster onboarding**: Consistent patterns across projects
- **Reduced cognitive load**: No decisions about file placement

### For Teams
- **Consistent codebases**: All projects follow same structure
- **Easy code reviews**: Focus on logic, not structure
- **Simplified maintenance**: Standard patterns for updates

### For Projects
- **Scalable architecture**: Structure that grows with the project
- **Easy refactoring**: Predictable file locations
- **Better tooling**: IDEs and tools work optimally

## Migration and Updates

When standards evolve, SubZero provides migration tools:

```bash
# Migrate to new standards
subzero-cli migrate --standards=v2

# Preview migration changes
subzero-cli migrate --dry-run

# Migrate specific module
subzero-cli migrate --module=tables --standards=v2
```
